## 2026-05-13：Block A — Le2i 資料集取得與處理

**目標：**
原訓練集（URFD）只有 1 個房間、1 位受試者、固定光線，模型無法泛化到真實場景。引入 Le2i Fall Detection 資料集來解決單一場景問題。

**做了什麼：**
- 透過 Kaggle CLI 下載 Le2i 資料集（9.37 GB），確認 `kaggle.json` 就位
- 解壓後刪除所有 PNG 圖片（節省磁碟空間），只保留 `.avi` 影片
- 識別六個場景：Coffee_room_01、Coffee_room_02、Home_01、Home_02、Lecture_room、Office
- 確認 annotation 情況：Home/Coffee 四場景有 `.txt` 標記跌倒起始∕結束幀；Lecture_room 與 Office 無 annotation
- 執行 `convert_le2i.py`：MediaPipe 逐幀提取骨架座標 → 滑動視窗（FRAME_LEN=30, STEP=15）→ 存成 `.npy`
- 標記規則：窗口內任一幀落在 `[fall_start, fall_end]` → label=1，否則 → label=0

**結果：**
- Le2i 新增：fall=335 筆、normal=2119 筆（共 130 支有效影片）
- `collected_data/` 累計：fall=559、normal=2433（含原 URFD 資料）
- Lecture_room（27 支）與 Office（33 支）因無 annotation 跳過，暫不使用

**為什麼這樣做：**
URFD 資料集只有 1 個受控環境，直接拿來評估跨場景效果等同隨機猜測（Block B 驗證）。Le2i 提供多場景、多視角、不同光線條件，是目前公開跌倒資料集中場景多樣性最高的之一，加入後能讓模型接觸真實部署環境。

**產出檔案：**
- `convert_le2i.py`（轉換腳本）
- `collected_data/f_*.npy`、`collected_data/n_*.npy`（新增 Le2i 窗口樣本）
- `datasets/le2i/`（原始影片，保留 `.avi`）

## 2026-05-13：Block B — v1 Baseline 評估

**目標：**
在引入 Le2i 資料重訓之前，先量化 v1 模型（URFD only 訓練）在 Le2i 上的泛化能力，確立改善基準線。

**做了什麼：**
- 以 `evaluate_baseline.py` 載入 `best_fall_detection_model.h5`（v1，URFD only）
- 在 Le2i hold-out test set（n=335；fall=48, normal=287）上進行預測
- 計算 AUC、Fall Precision/Recall/F1、Normal F1、Accuracy
- 與後續 v2 對比，構成評估基準

**結果：**
| 指標 | v1 (URFD only) |
|---|---|
| AUC | 0.5495 |
| Fall Recall | 0.2708 |
| Fall F1 | 0.2385 |
| Normal F1 | 0.8520 |
| Accuracy | 0.7522 |

- AUC=0.5495 ≈ 隨機猜測（0.5）
- Fall Recall=0.27：每 4 次跌倒只抓到 1 次
- 結論：v1 對 Le2i 場景幾乎無泛化能力

**為什麼這樣做：**
沒有 baseline 就無法衡量改善幅度。Block B 的數字讓我們能在報告中清楚呈現 v2（甚至 v4）的進步量，也確認了「跨資料集訓練」的必要性。

**產出檔案：**
- `evaluate_v2.py`（含 v1 vs v2 對比邏輯）
- `v2_classification_report.txt`（v1 baseline 數字保存其中）

## 2026-05-13：Block C — v2 訓練（跨資料集 + 數據增強 + class_weight）

**目標：**
解決 v1 泛化失敗問題，透過三個策略同步提升：引入 Le2i 資料、處理 fall/normal 嚴重不平衡、增加資料多樣性。

**做了什麼：**
- **C1** `prepare_v2_dataset.py`：切分 train/val/test（Le2i 70/15/15，URFD 全進 train），SEED=42 確保可重現
  - Train: URFD 284 筆 + Le2i 70%（~1558 筆）
  - Val/Test: Le2i 各 15%（各 335 筆），test.npz 為 hold-out
- **C2** `augmentation.py`：實作三種增強（機率 p=0.5）
  - `horizontal_flip`：左右翻轉 x 座標
  - `time_warp`：時間軸微小扭曲
  - `landmark_jitter`：骨架點座標加入高斯雜訊
- **C3** `train_model_v2.py`：LSTM 模型訓練
  - 架構：LSTM(64) → BN → Dropout(0.4) → LSTM(32) → BN → Dropout(0.4) → Dense(16) → Dense(1, sigmoid)
  - 超參數：LR=1e-4, BATCH=32, EPOCHS=100, L2=1e-3
  - class_weight 自動計算（sklearn balanced）：normal≈0.563、fall≈4.497
  - EarlyStopping patience=10，best epoch=75，val_acc=0.8925
- **C4** `evaluate_v2.py`：在 test.npz 上評估，同時輸出 v1 vs v2 對比表

**結果：**
| 指標 | v1 | v2 |
|---|---|---|
| AUC | 0.5495 | **0.9464** |
| Fall Recall | 0.2708 | **0.7708** |
| Fall F1 | 0.2385 | **0.6491** |
| Normal F1 | 0.8520 | **0.9281** |
| Accuracy | 0.7522 | **0.8806** |

- AUC 從 0.55 → 0.9464（+0.40）
- Fall Recall 從 0.27 → 0.77（+185%）
- 產出 `v2_confusion_matrix.png`、`v2_roc_curve.png`

**為什麼這樣做：**
單靠加資料不夠，因為 Le2i 的 fall:normal 比例約 1:6，若不加權模型會偏向預測 normal。class_weight 讓 fall 樣本有效權重放大 ~4.5 倍，搭配 augmentation 避免 overfitting，三者缺一不可。

**產出檔案：**
- `prepare_v2_dataset.py` / `augmentation.py` / `train_model_v2.py` / `evaluate_v2.py`
- `best_fall_detection_model_v2.h5`（best epoch=75）
- `fall_detection_model_v2.h5`（final epoch）
- `train.npz` / `val.npz` / `test.npz`
- `v2_classification_report.txt` / `v2_confusion_matrix.png` / `v2_roc_curve.png`

## 2026-05-13：Block D — v2 部署（閾值優化 + TFLite 匯出）

**目標：**
將訓練好的 v2 模型轉化為可即時推論的部署格式，並調整閾值以符合「優先不漏報」的安全需求。

**做了什麼：**
- **D1** `tune_threshold.py`：掃描閾值 0.30～0.70（步長 0.05）
  - `threshold_safe=0.30`：Fall Recall≥0.85 的最低閾值
  - `threshold_balanced=0.65`：Fall F1 最高的閾值
  - 產出 `threshold_analysis.png`、`thresholds.json`
- **D2** `export_tflite_v2.py`：Keras H5 → TFLite
  - 啟用 `SELECT_TF_OPS`（支援 LSTM 中的 TensorList ops）
  - `fall_detection_model_v2.tflite`：235.1 KB
- **D3** `realtime_predict_v2.py`：攝像頭即時推論腳本
  - 從 `thresholds.json` 讀取 `threshold_safe`
  - 滑動視窗（deque maxlen=30）+ 連續 3 幀超閾值才觸發警報
  - UI：機率條 + FALL DETECTED 大字 + 紅框
- **D4** 主目錄整理：v1 腳本歸檔至 `Archive/v1/`

**結果：**
- `threshold_safe=0.30`（Fall Recall=0.90）
- `threshold_balanced=0.65`（Fall F1=0.71）
- TFLite 模型 235.1 KB，可在 Apple M4 Pro 即時推論
- `realtime_predict_v2.py` 確認可啟動並正常顯示骨架疊圖

**為什麼這樣做：**
跌倒漏報（FN）的代價遠高於誤報（FP）——漏掉一次真實跌倒可能危及生命，而誤報只是干擾。因此採用 threshold_safe=0.30 作為主要部署閾值，接受更高 FP 率換取更高 Recall。TFLite 是為了未來部署到手機 App 做準備。

**產出檔案：**
- `tune_threshold.py` / `export_tflite_v2.py` / `realtime_predict_v2.py`
- `thresholds.json`（threshold_safe=0.30, threshold_balanced=0.65）
- `fall_detection_model_v2.tflite`（235.1 KB）
- `threshold_analysis.png`
- `Archive/v1/`（v1 腳本歸檔）

## 2026-05-13：Block E — 視覺化驗證

**目標：**
在送報告前對模型進行質性驗證——眼睛看到骨架跟機率曲線，確認 TP/FN/FP/TN 各類案例符合預期，並發現量化指標無法反映的問題。

**做了什麼：**
- **E1** `video_visualize.py`：影片視覺化工具
  - 左側：原始影片 + MediaPipe 骨架疊圖
  - 右側：即時機率歷史長條圖（最近 150 次推論），橙色線標 threshold
  - 跌倒警示：紅框 + "FALL DETECTED" 大字
  - CLI 支援 `--slow`（0.5x）與 `--save output.mp4`
- **E2** `find_validation_samples.py`：自動選片工具
  - 跑 v2 模型對 Le2i 所有標注影片逐幀推論
  - 按 max_in（fall 幀最高機率）與 max_out（non-fall 幀最高機率）分類
  - 選出 TP×3 / FN×3 / FP×2 / TN×2，複製到 `validation_samples/`
- **E3** 確認 `realtime_predict_v2.py` 依賴正常啟動

**結果：**
- 選出 10 支驗證影片（詳見 PROJECT_STATUS.md Block E 表格）
- **重大發現**：Lecture_room / Office 的 16 支純 normal 影片，max_out 全數落在 0.59～0.99，幾乎全觸發警示
- 根本原因：這兩場景在訓練時因無 annotation 被排除，模型完全沒見過它們的 normal 樣貌

**為什麼這樣做：**
數字（AUC=0.9464）看起來很好，但視覺驗證揭示了量化指標無法看到的問題——模型在訓練場景以外的環境完全失效。這個發現直接推動了 Block F（場景泛化修補）的需求。

**產出檔案：**
- `video_visualize.py` / `find_validation_samples.py`
- `validation_samples/`（10 支標注影片：TP×3, FN×3, FP×2, TN×2）

## 2026-05-13：Block F — v3 訓練（場景泛化修補）

**目標：**
解決 Block E 發現的 Lecture_room / Office 全數誤報問題，透過加入這兩個場景的 normal 資料來讓模型學習它們的外觀。

**做了什麼：**
- **F1** `convert_le2i_extra.py`：處理無 annotation 的場景
  - Lecture_room（27 支）+ Office（33 支），共 60 支影片
  - 整支影片全部標 label=0（normal），滑動視窗（FRAME_LEN=30, STEP=15）
  - 前綴 `n_le2i_extra_`，存入 `collected_data/`
  - 新增：Lecture_room 897 筆、Office 905 筆，共 1802 筆
- **F2** `prepare_v3_dataset.py`：重新切分資料集
  - Train：URFD + Le2i Home/Coffee 70% + Lecture/Office extra 80%（3283 筆）
  - Val/Test：Le2i Home/Coffee 各 15%（與 v2 使用相同 SEED=42，test.npz 完全一致）
  - `test_extra.npz`：Lecture/Office extra 20%（361 筆，FP 評估用）
- **F3** `train_model_v3.py`：沿用 v2 架構，載入新訓練集
  - class_weight 繼續自動計算（fall≈4.5x）
  - best epoch=24，val_acc=0.8537
- **F4** `evaluate_v3.py`：雙重評估
  - test.npz（Le2i hold-out）+ test_extra.npz（FP 改善驗證）

**結果：**
| 指標 | v2 | v3 |
|---|---|---|
| AUC | **0.9464** | 0.8910 ↓ |
| Fall Recall | 0.7708 | **0.8333** ↑ |
| Fall F1 | **0.6491** | 0.5926 ↓ |
| FP 率（extra） | 13.0% | **5.3%** ↓ |

- FP 率從 13%→5.3%（顯著改善），但 AUC 和 F1 退步
- Trade-off 根因：class_weight 自動計算在 fall:normal=1:8 的新比例下，normal 權重過低，導致 Precision 下降

**為什麼這樣做：**
視覺驗證（Block E）確認 FP 問題是真實部署的最大障礙。加入 Lecture/Office normal 資料是最直接的修法，但 v3 暴露了 class_weight 自動計算在高度不平衡資料下的局限，促使 Block G 採用手動調整策略。

**產出檔案：**
- `convert_le2i_extra.py` / `prepare_v3_dataset.py` / `train_model_v3.py` / `evaluate_v3.py`
- `collected_data/n_le2i_extra_*.npy`（1802 筆）
- `test_extra.npz`
- `Archive/v3/`（v3 模型與評估結果歸檔）

## 2026-05-14：Block G — v4 訓練（訓練配方優化）與部署

**目標：**
在保住 v3 場景泛化改善（FP↓）的前提下，修復 AUC 和 F1 退步。策略：用 Hard Negative Oversampling 強調 Lecture/Office normal，同時改用手動 class_weight 避免自動計算在極度不平衡下失準。

**做了什麼：**
- **G1** `train_model_v4.py`：v4 訓練
  - **改動 1**：class_weight 改為手動 `{0: 1.0, 1: 3.0}`（不再 sklearn 自動計算）
  - **改動 2**：Hard Negative Oversampling——Lecture/Office extra train 部分再複製 2 份加入訓練集
    - 最終 extra normal 在訓練中出現 3x（1x from train.npz + 2x duplicate）
    - 訓練集：fall=365, normal=5800，比例 1:15.9
  - 架構不變（LSTM 64→32→Dense 16→sigmoid）
  - EarlyStopping patience=10，best epoch=68，val_acc=0.8955
- **G2** `evaluate_v4.py`：四欄對比（v1/v2/v3/v4）+ FP 報告

**G1+G2 結果：**
| 指標 | v2 | v3 | **v4** |
|---|---|---|---|
| AUC | **0.9464** | 0.8910 | 0.9426 |
| Fall Precision | 0.5606 | 0.4598 | **0.6129** |
| Fall Recall | 0.7708 | **0.8333** | 0.7917 |
| Fall F1 | 0.6491 | 0.5926 | **0.6909** |
| Normal F1 | 0.9281 | 0.8972 | **0.9393** |
| Accuracy | 0.8806 | 0.8358 | **0.8985** |
| FP 率（extra @0.5） | 13.0% | 5.3% | **1.1%** |

- G3 決策：✅ v4 為新主力（AUC=0.9426 ≥ 0.93 且 FP=1.1% < 10%）

**G 收尾（部署化）：**
- **G5** `tune_threshold_v4.py`：重新調閾值
  - `threshold_safe=0.30`（Fall Recall=0.875，FP_extra=1.9%）
  - `threshold_balanced=0.45`（Fall F1=**0.708**，整個專題最高，FP_extra=1.4%）
  - 產出 `threshold_analysis_v4.png`、`thresholds_v4.json`
- **G6** `export_tflite_v4.py`：匯出 `fall_detection_model_v4.tflite`（235.1 KB）
- **G7** `realtime_predict_v4.py`：攝像頭主力腳本
  - 載入 v4 TFLite + `thresholds_v4.json`
  - UI 顯示「Model: v4 | Threshold: 0.30」
- **G8** 主目錄整理：v3 相關檔案歸檔至 `Archive/v3/`

**為什麼這樣做：**
v3 的失敗告訴我們，class_weight 自動計算在 fall:normal=1:8 時會讓 normal 的懲罰太輕。手動設 {0:1.0, 1:3.0} 讓 fall 有 3x 懲罰（而非 sklearn 算出的 4.5x），在極度不平衡的 normal 下反而更平衡。Hard Negative Oversampling 讓模型對「困難的 normal 場景」多看兩倍，直接壓制 FP。

**產出檔案：**
- `train_model_v4.py` / `evaluate_v4.py`
- `best_fall_detection_model_v4.h5`（best epoch=68）
- `fall_detection_model_v4.tflite`（235.1 KB）
- `thresholds_v4.json`（safe=0.30, balanced=0.45）
- `tune_threshold_v4.py` / `export_tflite_v4.py` / `realtime_predict_v4.py`
- `threshold_analysis_v4.png`
- `v4_classification_report.txt` / `v4_confusion_matrix.png` / `v4_roc_curve.png`
- `Archive/v3/`（v3 歸檔）
